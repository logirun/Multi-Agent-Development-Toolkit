## 1. 业务目标与背景
在传统的多 Agent 协同开发中，极易出现智能体集群合谋盲从与群体谄媚——即多个 Agent 相互盲目点赞、秒级合并不经审查的代码，导致幻觉代码大量流入主干。
AegisFlow（神盾协同微内核）的核心目标是构建一套具有**确定性机器门禁、物理权限隔离、独立一票否决权（QR/SR/FR/DR）和三振出局熔断机制**的虚拟软件工坊，实现“相互协同，相互制约”的研发闭环。


---

## 2. 核心功能需求

### 2.1 任务生命周期与分层网关 (Elastic Gateway)
- **Tier 0 (FLASH)**: 快速问答与单点咨询，0 延迟，不创建工单卡片，不走门禁。
- **Tier 1 (PATCH / SPIKE)**: 小型修补与技术探针，跳过契约冻结，但保留代码审查与自动化测试门禁。
- **Tier 2 (CORE)**: 标准功能特性研发，严格遵守单一职责原则（SRP $\le 8.0\text{h}$），走完整六重门禁。
- **Tier 3 (ENTERPRISE)**: 架构重构、DB 变更、安全核心，需经过架构师 ADR 与 CTO 联合审查。

### 2.2 六重确定性质量门禁 (Deterministic Quality Gates)
1. **Gate 1 (架构与契约冻结)**: 契约规范经架构师审查后，计算 SHA256 摘要并写死，开发阶段禁止篡改。
2. **Gate 2 (代码质量与 Git 提交规范)**: 遵循 Conventional Commits v1.0.0 格式，通过 SWE-agent 级快速 AST 语法检查。
3. **Gate 3 (安全审查一票否决门禁)**: 扫描硬编码密钥、OWASP Top 10 漏洞、危险系统执行（`eval/exec`），安全工程师拥有 `#SR` 一票否决权。
4. **Gate 4 (自动化测试与防作弊门禁)**: 开发人员严禁修改 `tests/`，QA 工程师在干净隔离环境中执行全量自动化测试，拥有 `#FR` 一票否决权。
5. **Gate 5 (活文档与代码同步门禁)**: API 路由或接口变更必须同步更新 `docs/api/` 或 README，文档工程师拥有 `#DR` 一票否决权。
6. **Gate 6 (人类物理最终验收门禁)**: 严禁 Agent 伪造人类批准，必须在交互式终端经人类操作员键盘确认（`[y/N]`）方可标记为 `ACCEPTED`。

### 2.3 防作弊与权限物理隔离 (Role Least-Privilege Lockdown)
- **架构师 (Architect)**: 物理禁止写入 `src/`，仅允许编写 `docs/contracts/` 与 `docs/adr/`。
- **开发者 (Developer)**: 物理禁止写入 `tests/`，杜绝“为跑通自测而修改测试断言”的作弊行为。
- **测试工程师 (QA Tester)**: 物理禁止写入 `src/`，只能编写测试用例或提交 `#FR-x` 缺陷打回。
