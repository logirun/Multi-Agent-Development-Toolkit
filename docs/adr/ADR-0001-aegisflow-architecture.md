## 1. 背景与问题陈述
在大语言模型驱动的多 Agent 软件工程场景中，Agent 常常出现由于上下文窗口丢失、指令漂移或合谋盲从（Groupthink）导致的代码腐化。
市面上现有的多 Agent 框架（如 MetaGPT, ChatDev）多为单向瀑布流水线，缺乏运行时强制性约束机制，且容易在多轮迭代中产生数百条无效任务卡片，引发严重的 Token 膨胀。

---

## 2. 决策考量与架构选择

### 2.1 采用双引擎看板与 Top-5 防 Token 膨胀机制
- **问题**: 随着项目迭代，工单数量迅速增至数百个，在每次 CLI 或 Agent 调用时全量倾倒工单会导致 LLM 上下文爆炸。
- **决策**:
  1. 终端 ANSI 看板默认执行 **Top-5 活跃工单过滤**，仅向 LLM 上下文暴露最关键的 5 张进行中卡片。
  2. 提供零依赖本地 Web 看板（基于标准库 `http.server`，端口 8848），供人类工程师在浏览器中浏览全量生命周期。

### 2.2 确立四维独立一票否决权 (Veto Powers) 与三振出局熔断机制
- **决策**:
  - 代码评审员（`#QR`）：代码质量与 Conventional Commits 规范一票否决。
  - 安全审计员（`#SR`）：密钥泄露、OWASP 与注入漏洞一票否决。
  - 质保测试员（`#FR`）：自动化回归与功能缺陷一票否决。
  - 文档专家（`#DR`）：代码与文档不同步一票否决。
- **制衡规则**:
  - 任何角色行使否决权时，工单不会生成新的 ID，而是生成派生打回标签（如 `TSK-1001#QR-1`）。
  - 若累计打回达到 3 次，触发**熔断协议 (Circuit Breaker)**，工单立即锁定为 `BLOCKED`，移交 CTO 或人类裁决，防止无限递归死循环。

### 2.3 基于 SHA256 与非对称签名的密码学收据 (Cryptographic Receipts)
- **决策**:
  - 每当一个阶段门禁通过时，Gatekeeper 引擎自动生成一个格式为 `REC-<TaskID>-<GATE>-PASS.json` 的不可篡改机器收据。
  - 收据包含测试执行耗时、覆盖率、Git commit sha 与 SHA256 签名，附着在工单交付物清单中。

### 2.4 基于 LangGraph 理念的时光倒流 (Time-Travel Rollback)
- **决策**:
  - 状态机在每一次状态跃迁（`BACKLOG` -> `IN_PROGRESS` -> `CODE_REVIEW` 等）时自动在 `.virtual_company_board.json` 中保存快照切片（保留最近 10 个快照）。
  - 当代码审查或安全测试发现灾难性架构偏差时，CTO 或人类操作员可一键回滚工单状态至任意历史检查点。

---

## 3. 产生的影响与后果
- **正面影响**:
  - 杜绝了智能体集群盲从与群体谄媚，实现了机器级别的确定性质量保障与密码学闭环。

  - 严格限制了每个角色的权限边界，杜绝了开发人员擅改测试用例的作弊手段。
  - 保留了不可篡改的审计追踪链（EventStream 与 Receipts）。
- **负面影响 / 限制**:
  - 对于极微小的单行修补，完整走完门禁需要耗费一定校验时间。此限制通过 Tier 0（快速通道）与 Tier 1（轻量通道）得到有效缓解。
